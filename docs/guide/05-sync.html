Part 5The sync server

apps/sync is the backend. It is about thirty small classes. This part goes through them folder by folder, then shows how they are wired together.

apps/sync/src/
├── index.ts               the entry point: read settings, start the server
├── SyncServer.ts          builds every object and connects them ("composition root")
├── config/Config.ts       reads and validates environment variables
├── logging/Logger.ts      structured logs
├── errors/                the kinds of expected failure
├── identity/NodeIdentity.ts   this server's unique id
├── auth/                  edit tokens and permissions
├── http/                  ordinary web routes
├── ws/                    WebSocket connections
├── rooms/                 documents held in memory
├── pubsub/                talking to other servers through Redis
├── persistence/           talking to Postgres
├── metrics/MetricsRegistry.ts counters and timings
├── lifecycle/GracefulShutdown.ts stopping without losing data
└── testing/ProtocolClient.ts  a browser-less client used by tests and scripts

5.1 The foundations

ClassWhat it does
ConfigThe only place environment variables are read. A Zod schema checks them all at start-up. If something is missing or malformed, the server refuses to start and prints exactly which variable is wrong. Everything else asks config.databaseUrl, config.flushIntervalMs and so on, already typed.
LoggerA thin wrapper around Pino. logger.child({ roomSlug }) returns a logger that adds that context to every line. It automatically hides anything named token or url, so edit tokens cannot leak into logs.
DomainError and its childrenExpected failures, each with a machine-readable kind and an HTTP status: NotFoundError (404), UnauthorizedError (401), ProtocolError (400), ValidationError (400). Code throws these; one place turns them into responses.
NodeIdentityGenerates one random id (a UUID) when the process starts. It is stamped on every Redis message for echo suppression, and its short name appears in the editor's status bar.
MetricsRegistryHolds every counter and timer: open connections, rooms in memory, messages by type, broadcast latency, flush duration, compactions, and more.

5.2 auth/: who may edit

FileWhat it does
Permission.tsTwo values: READ and WRITE.
TokenService.tsmintEditToken(slug) creates a new token and the hash to store. verifyEditToken(slug, token, hash) checks a token in constant time. Part 9 explains the cryptography.

5.3 http/: the ordinary routes

ClassWhat it does
HttpServerCreates the Hono app, adds logging, CORS and a body-size limit, mounts the routes, and listens on the port. When a request asks to upgrade to a WebSocket, it hands the request to the WebSocketGateway.
RoomsRoutesPOST /rooms creates a room and returns its slug and edit token (the only time the token is ever sent). GET /rooms/:slug/meta returns the room's language and title.
HealthRoutes/healthz: "the process is alive". /readyz: "Postgres and Redis answer, and I am not shutting down". Load balancers use the second to decide whether to send traffic.
MetricsRoutes/metrics in the Prometheus text format.
RequestLoggerOne log line per HTTP request, path only (never the query string).
ErrorHandlerTurns any thrown error into { status: "error", kind, message }. Unknown errors are logged in full but reveal nothing to the caller.

5.4 ws/: the WebSocket layer

ClassWhat it does
WebSocketGatewayThe front door. For a request to /ws/<slug>?t=<token> it checks the path and the browser origin, asks the RoomManager for the room, decides the permission (no token: read; valid token: write; wrong token: refused), completes the upgrade, and creates a RoomSession.
RoomSessionOne object per connected browser. It decodes each incoming frame and routes it: sync messages and updates to the Room, pings answered directly. It enforces permission: an update from a read-only socket gets an ERROR frame and is disconnected. It also remembers which cursors this socket introduced, so they can be removed when it leaves.
MessageCodecThe server's wrapper around the shared Codec; converts decoding failures into ProtocolError.
HeartbeatManagerEvery 30 seconds it pings every socket. A socket that did not answer the previous ping is terminated. Without this, a laptop that went to sleep would stay "connected" forever.
BackpressureGuardBefore each send, checks how many bytes are waiting to go out to that socket. If a slow client has more than 4 MB queued, it is disconnected. It loses nothing: on reconnect it catches up with one diff.

5.5 rooms/: documents in memory

This folder is the core of the server.

ClassWhat it does
RoomOne collaborative document, live in this server's memory. It owns the Yjs document and the awareness object, the set of sessions attached to it, and a list of updates not yet saved (the "dirty set"). It applies incoming changes, answers sync requests, and schedules saves.
RoomManagerA map from slug to Room. get(slug) returns the room if it is already in memory; otherwise it loads it. If fifty people ask for the same cold room at once, they share one load. When a room has had no connections for five minutes, it is saved and removed from memory ("evicted").
RoomHydratorRebuilds a document from Postgres: apply the latest snapshot, then every update row after it. "Hydrate" means "fill an empty object with its saved data".
RoomBroadcasterFan-out. Given a change, send it to the sockets on this server and, if it originated here, publish it to Redis.
UpdateOriginTwo markers, REDIS and HYDRATE, used to label where a change came from.
SlugGeneratorMakes random 10-character room ids.

The origin rule

Every change applied to a Yjs document carries a label called its origin. In this server the origin is either the RoomSession the change came from, or one of the two markers. That single label decides everything that happens next:

The change came from…Send to local sockets?Publish to Redis?Save to Postgres?
a browser on this serverYes, all except the senderYesYes
another server, via RedisYes, allNo (it would loop)No (the other server saves it)
Postgres, while loadingNobody is attached yetNoNo (it is already there)
Why it is built this wayEvery edit reaches every server, but it originates on exactly one: the server the typing user is connected to. If only the originating server saves it, each edit is written to the database exactly once, with no leader election and no locks.

5.6 pubsub/: talking to the other servers

FileWhat it does
RedisPubSubOwns two Redis connections, because a connection that has subscribed cannot do anything else: one to publish, one to listen. It wraps outgoing messages in an envelope, drops incoming messages carrying its own id, and hands the rest to the right room. It also notices when the listening connection was lost and restored.
MessageEnvelopeThe layout of a Redis message: 16 bytes of node id, 1 byte of kind, then the payload. Kinds are update, awareness and sync-request.
RoomChannelsBuilds channel names like room:<slug>:updates and parses them back.
RoomBusAn interface: the three operations rooms need (subscribe, unsubscribe, publish). The real implementation is RedisPubSub; tests swap in a fake that needs no Redis.

5.7 persistence/: talking to Postgres

ClassWhat it does
DatabaseHolds the connection pool; offers transaction(), ping(), migrate() and close().
RoomRepositoryThe rooms table: create a room, find one by slug, update its "last active" time and settings.
UpdateRepositoryThe document_updates table: append a batch, read rows back in order in pages of 500, count them, delete up to an id.
SnapshotRepositoryThe document_snapshots table: find the latest, insert a new one, remove the old ones.
CompactionJobEvery 60 seconds, for each room in memory with more than 1,000 update rows, folds the rows into one snapshot. Explained step by step in Part 7.

A repository is a class whose only job is to read and write one table. The rest of the code calls updates.appendBatch(...) and never writes SQL.

5.8 lifecycle/GracefulShutdown.ts

When the operating system asks the server to stop (the SIGTERM signal, sent on every deploy), this class runs an ordered teardown so that no edit is lost:

  1. Stop accepting: /readyz starts answering 503 and new WebSockets are refused.
  2. Stop the background timers (compaction, heartbeat).
  3. Close every socket with code 1001, "going away", and save every room that has unsaved edits. The browsers will reconnect to another server.
  4. Disconnect from Redis, then from Postgres.
  5. Release the network port and exit.

If this takes longer than 25 seconds, the process exits anyway, just before the platform would kill it at 30.

5.9 How it is all wired: SyncServer.ts

index.ts is five lines: read the config, create a SyncServer, install the shutdown handler, call start(). SyncServer is the one place that knows about every class. Its constructor creates each object once and passes it to the objects that need it:

This object……is given these
Databasethe database address from Config
the three repositoriesDatabase
RoomHydratorSnapshotRepository, UpdateRepository
RedisPubSubthe Redis address, NodeIdentity, Logger, MetricsRegistry
RoomBroadcasterRedisPubSub
RoomManagerRoomRepository, RoomHydrator, RoomBroadcaster, UpdateRepository, RedisPubSub
CompactionJobDatabase, the snapshot and update repositories, RoomHydrator, and the list of rooms in memory from RoomManager
WebSocketGatewayRoomManager, TokenService, MessageCodec, HeartbeatManager, NodeIdentity
HttpServerthe three route classes and the WebSocketGateway
GracefulShutdownHttpServer, RoomManager, and the stop functions of the compaction job, heartbeat, Redis and database

This pattern is called dependency injection: a class does not create the things it depends on; it is given them. The pay-off is in testing. A test can build a Room with a fake database and a fake bus and check its behaviour in a millisecond. And because one SyncServer object is one complete node, the most important test in the project simply creates two of them in the same process.

start() does things in a safe order: optionally apply migrations, check Postgres answers, connect to Redis, start listening, start the heartbeat and compaction timers.
