Part 9Security, testing and operations

9.1 Share links without accounts

There is no user table and no login. Instead, holding the link is the permission. This idea is called a capability: like a key, whoever holds it may use it.

A room has two links:

https://…/r/k3x9m2p7qa                      view only
https://…/r/k3x9m2p7qa#t=9SiOLqw77ML_C8o…   can edit

The part after # is called the URL fragment. Browsers never send the fragment to a web server. So the token does not appear in server logs, and is not leaked to other sites through the Referer header. The page reads it with JavaScript and passes it along when opening the WebSocket.

How the token is made

You need one concept: HMAC. An HMAC takes a secret key and a message, and produces a fixed-length fingerprint. Without the key you cannot produce the right fingerprint, and you cannot work backwards from the fingerprint to the key or the message.

roomSecret = 32 random bytes                              exists only for an instant
token      = base64url( HMAC(roomSecret, "edit:" + slug) )   sent to the creator, once
tokenHash  = hex( HMAC(EDIT_SECRET, slug + ":" + token) )    stored in rooms.edit_token_hash
  • The token is effectively 256 random bits. It cannot be guessed.
  • The database holds only tokenHash. Someone who stole the database could not turn that back into working links, because computing the hash also needs EDIT_SECRET, which lives only in the server's environment.
  • To verify, the server recomputes the hash from the token it was given and compares. The comparison uses timingSafeEqual, which takes the same time whether the values match or not, so an attacker cannot learn anything by measuring response times.

Enforcement

  • No token: the socket is marked READ. If it ever sends an UPDATE or SYNC_STEP_2, the server answers with an error and disconnects it. The read-only editor in the browser is a convenience; the real check is on the server.
  • Wrong token: refused outright, not quietly downgraded to read-only.
  • Names and colours that arrive from other users are treated as untrusted and cleaned before being shown.
  • The server only accepts WebSockets from the web origins listed in ALLOWED_ORIGINS.

9.2 The tests

There are three layers, from fast and narrow to slow and realistic.

LayerWhat it checksWhere
UnitOne class at a time, with fakes for everything else. Codec, envelope, tokens, backoff, the Room logic.apps/sync/test/unit, apps/web/test, packages/shared/test
IntegrationClasses against a real Postgres and a real Redis: repositories, hydration, compaction, pub/sub.apps/sync/test/integration
Protocol end-to-endWhole servers started inside the test, with browser-less clients (ProtocolClient) connecting over real WebSockets.apps/sync/test/e2e-protocol
Browser end-to-endPlaywright drives real Chromium windows: two people in a room, view-only link, reload, share dialog.apps/web/e2e

The single most important file is convergence.test.ts. It starts two sync nodes sharing one Postgres and one Redis, connects one client to each, has both type at the same position a hundred times, and asserts that both clients and both servers end with identical text. That test is the horizontal-scaling claim, proven mechanically.

ClaimHow a test proves it
Clients on different servers convergeThe convergence test above.
Reconnecting costs a diff, not a replayDrop a client from a 20 KB document, edit on both sides, reconnect: catch-up must be under 200 bytes.
A restart loses nothingType, shut the server down before the save timer fires, start a new one, read the text back.
Each edit is saved exactly once5 edits via node A and 3 via node B must produce 5 and 3 rows.
Compaction is safe under loadTen compactions racing ten writers; result compared exactly.
View-only really is view-onlyA read socket forges write frames; both rejected, document unchanged.

9.3 Operations

Health and metrics

Try itWith the server running: 
curl localhost:4000/healthz        # {"status":"ok","node":"…"}
curl localhost:4000/readyz         # checks Postgres and Redis
curl -s localhost:4000/metrics | grep synccode_   # live counters

Useful metrics: synccode_ws_connections (open sockets), synccode_hot_rooms (rooms in memory), synccode_broadcast_latency_seconds, synccode_updates_persisted_total, synccode_room_hydration_seconds (cold-start time).

The scripts

CommandWhat it does
pnpm seedCreates three rooms with starter code and prints their edit and view links.
pnpm compactRuns compaction for every room in the database, including rooms nobody has open. Safe to run while servers are live.
pnpm load-testConnects 50 browser-less clients to one room, has them all type, and reports p50 / p95 / p99 delivery time and whether every copy ended identical.

Docker and the multi-node demo

docker/docker-compose.yml describes six containers: Postgres, Redis, sync-a, sync-b, nginx, and the web app. nginx is a load balancer: it accepts connections on one address and hands each new one to the next sync node in turn ("round robin"). Open a room in two tabs and the status bar shows Node sync-a in one and Node sync-b in the other, yet both show the same document.

Continuous integration

.github/workflows/ci.yml runs on every push: lint, type-check, all tests against real Postgres and Redis, a production build, then the browser tests. Only if everything passes on the main branch does it apply database migrations to production.
