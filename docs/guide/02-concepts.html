Part 2The concepts, from zero

Five concepts carry the whole project. Each is explained here without assuming you have met it before.

2.1 HTTP and WebSockets

HTTP is how browsers normally talk to servers. The browser sends a request ("give me this page"), the server sends a response, and the exchange is over. The server can never start a conversation.

A WebSocket starts as an ordinary HTTP request that says "I would like to upgrade". If the server agrees, the same network connection stays open, and from then on either side can send a message at any time. Messages can be text or raw bytes (binary). SyncCode uses binary messages only, because the document updates are already compact binary and wrapping them in text would make them bigger and slower.

HTTPWebSocket
Who can speakBrowser asks, server answersEither side, any time
ConnectionClosed after each exchangeStays open for minutes or hours
Used in SyncCode forCreating a room, loading pages, health checksEvery edit and every cursor movement

A long-lived connection brings new problems that HTTP never had: it can die silently (a laptop lid closes), one side can be too slow to keep up, and it must be re-established after a drop. Part 5 shows the classes that handle each of those.

2.2 CRDTs: a document that merges itself

CRDT stands for Conflict-free Replicated Data Type. Take the words one at a time:

  • Replicated: there are many copies (replicas) of the data, one in each browser and one in each server.
  • Data type: here, a piece of text.
  • Conflict-free: any two copies can always be merged automatically, with no "your version or mine?" question.

The older approach, used by early Google Docs, is called operational transformation: one central server receives every edit and rewrites it to account for edits it raced with. It works, but everything must pass through that one clever server, and the rewriting rules are famously hard to get right. A CRDT moves the cleverness into the data itself, so the server can be simple. In SyncCode the server never looks inside an edit. It stores bytes and forwards bytes.

How Yjs represents text

We use a library called Yjs. Its algorithm is known as YATA. In Yjs, text is not a string. It is a chain of items, where an item is one or more characters plus some bookkeeping:

FieldMeaning
idA pair (clientID, clock). clientID is a random number each copy of the document picks for itself. clock counts how many characters that client has inserted so far. Together they are unique in the whole world, without asking anybody.
originThe id of the item that was immediately to the left when this one was typed.
rightOriginThe id of the item immediately to the right at that moment.
contentThe characters themselves.

The key shift: an insertion does not say "put x at position 5". Positions change as other people type. It says "put x between these two specific items", and item ids never change.

The conflict, solved

Back to the example. The text is A B. You (client 7) and your friend (client 9) both insert between A and B at the same time.

You:     item (7, 0)  content "x"   origin = A   rightOrigin = B
Friend:  item (9, 0)  content "y"   origin = A   rightOrigin = B

Both items claim the same gap. YATA's rule for this is fixed and simple: when two items have the same origin, order them by clientID. Every copy of the document applies the same rule to the same two ids, so every copy puts them in the same order. That one deterministic tie-break is what makes the whole thing converge. It is a mathematical property of the algorithm, not something that works "most of the time".

Try itOpen http://localhost:3000/engineering and scroll to "Why edits never conflict". Two real Yjs documents run in the page. Press Both type at the same spot, watch the two boxes differ, then press Reconnect.

Deleting

If deleting removed an item entirely, a friend's insertion that named it as its origin would have nothing to attach to. So a delete only marks the item as deleted (a "tombstone"). The characters are discarded to save space; a small marker stays. One consequence: a Yjs document's size reflects its history, not only its current text.

Updates: the unit that travels

Whenever a document changes, Yjs can describe the change as an update: a small block of bytes. Updates have three properties the entire backend relies on:

PropertyMeaningWhat it lets us do
IdempotentApplying the same update twice changes nothing the second time.We never have to worry about duplicates. Two servers can both apply the same update safely.
CommutativeApplying updates in any order gives the same document.Messages may arrive out of order. If one arrives before something it depends on, Yjs holds it until the missing piece shows up.
MergeableMany updates can be combined into one that means the same.We can squash a long history into one snapshot (Part 7).

In code, the whole API we need is four functions:

Y.applyUpdate(doc, update)                 // merge an update into a document
Y.encodeStateAsUpdate(doc)                 // the whole document as one update
Y.encodeStateVector(doc)                   // "what I have" (next section)
Y.encodeStateAsUpdate(doc, stateVector)    // only what the owner of that vector is missing

2.3 State vectors: catching up cheaply

Suppose you were offline for ten minutes and your friends made 10,000 edits. Resending the whole document, or replaying 10,000 messages, would be wasteful. Yjs has a neat answer.

A state vector is a short list that says, for each client, how many of their characters you have seen:

Your state vector:      client 7 → 41     client 9 → 17
The server's:           client 7 → 41     client 9 → 60     client 12 → 8

Comparing the two, the server knows exactly what you lack: client 9's items numbered 17 to 59, and all eight of client 12's. It packs just those into one update and sends it. The conversation is two messages:

you → server    SYNC_STEP_1   "here is my state vector"
server → you    SYNC_STEP_2   "here is exactly what you are missing"

Then the same thing happens in the other direction, so anything you typed while offline reaches the server. The cost depends on how much was missed, never on how big the document is or how long you were away. One of our tests proves this: a client that drops off a 20,000-character document and comes back receives a catch-up message of under 200 bytes.

In plain wordsInstead of asking "send me everything", you say "I have read up to page 41 of Alice's notes and page 17 of Bob's". The reply contains only the pages after those.
Why it is built this wayNotice that nothing is queued while you are offline. Your local document already contains your offline edits; the state-vector exchange finds and sends them. "The document is the queue" removes a whole category of bugs.

2.4 Awareness: cursors and presence

Where your cursor is, what you have selected, your name and your colour are not part of the document. Nobody needs yesterday's cursor position. Yjs handles this with a separate, simpler mechanism called awareness:

  • Each client owns exactly one entry, a small JSON object such as { user: { name, color }, selection: {…} }.
  • When you change it, the new version replaces the old one everywhere (last write wins). No merging is needed.
  • Every client re-announces its entry every 15 seconds. An entry not refreshed for 30 seconds is dropped. So someone who vanishes without saying goodbye still disappears from everyone's screen.
  • It is never saved to the database.

Cursor positions are stored as "next to this item", not "at index 12", so your cursor stays attached to the right character while other people type before it.

2.5 Redis pub/sub: how servers talk to each other

Redis is an in-memory data store. We use exactly one of its features: publish/subscribe. A program can SUBSCRIBE to a named channel; any program can PUBLISH a message to that channel; every subscriber receives it immediately. Redis does not keep the message. If nobody is listening, it is gone.

Each room gets two channels, named after the room's id (its slug):

room:k3x9m2p7qa:updates      document updates (and requests to catch up)
room:k3x9m2p7qa:awareness    cursor and presence changes

A sync node subscribes to a room's channels when the first user of that room connects to it, and unsubscribes when the room goes idle.

The echo problem

When node A publishes an update, Redis delivers it to all subscribers, and node A is one of them. If A treated its own message as news, it would apply it and publish it again, forever. The fix is a label. Every node picks a random id when it starts. Every message it publishes begins with that id. On receiving a message, a node looks at the label first, and drops the message if the label is its own. This is called echo suppression.

Why it is built this wayRedis also has "Streams", which remember messages. We deliberately use plain pub/sub, which forgets, because permanent storage is Postgres's job. The bus only has to make live servers agree right now. Anything a server misses can be recovered with a state-vector exchange, as Part 8 shows.
