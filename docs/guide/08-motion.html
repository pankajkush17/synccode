Part 8The system in motion

Now that you know the pieces, here is what they do together in each situation, naming the class responsible at every step.

8.1 Creating a room

  1. You press Start a room. StartRoomForm sends POST /api/rooms to the web app's own server.
  2. app/api/rooms/route.ts validates the request and forwards it to the sync server's POST /rooms. The browser never talks HTTP to the sync server directly.
  3. RoomsRoutes asks SlugGenerator for a random slug and TokenService for a new token and its hash.
  4. RoomRepository.create() inserts the row. In the very rare case that the slug already exists, it retries with a new one.
  5. The response { slug, editToken, language } travels back. This is the only time the token ever leaves the server.
  6. The browser navigates to /r/<slug>#t=<editToken>.

8.2 Joining a room: the handshake

On the server side, the first line triggers this chain: HttpServer sees the upgrade request and passes it to WebSocketGateway, which calls RoomManager.get(slug) (loading the room from Postgres if needed), checks the token with TokenService, completes the upgrade, creates a RoomSession, and calls room.attach(session), which sends AUTH_ACK.

If the room does not exist or the token is wrong, the server still completes the WebSocket handshake and then closes it immediately with code 4404 or 4401. This looks odd but is necessary: browsers hide the reason when an upgrade is refused, so this is the only way the page can tell "give up" from "try again".

8.4 Cursors and presence

The same route, with awareness instead of the document. Moving your cursor updates your awareness entry; the browser sends an AWARENESS frame; the server applies it to the room's awareness object, forwards it to local sockets and publishes it on the room's awareness channel. Nothing is saved. When a socket closes, its RoomSession removes the entries that socket introduced, and that removal is broadcast, so your cursor disappears from every screen at once.

8.5 Losing the connection

  1. The socket closes. ConnectionManager switches to RECONNECTING; the amber banner appears.
  2. The editor stays fully usable. Your keystrokes go into your local document as usual.
  3. ExponentialBackoff supplies the wait before each attempt: 0.5 s, 1 s, 2 s … up to 15 s. If the browser reports that the network is back, it retries at once.
  4. On reconnect, the handshake from 8.2 runs again. The two state-vector exchanges deliver what you missed and upload what you typed. The banner disappears.

If the server never told the browser it was closing (for example the wifi simply vanished), the browser may not notice for a long time. So the client also watches for silence: if no message at all has arrived for 20 seconds, it treats the connection as dead and starts reconnecting.

8.6 A second server joins in

Your friend's connection lands on node B, which has never seen this room. RoomManager.load() does three things in a deliberate order:

  1. Subscribe to the room's Redis channels first. From this moment node B will not miss anything new.
  2. Load from Postgres (snapshot, then updates).
  3. Publish a sync-request containing its state vector. Node A, which holds the room, replies with whatever node B lacks, and with the current list of cursors.
Why it is built this wayNode A saves edits at most 500 ms after they happen. So for up to half a second, an edit exists only in node A's memory. If node B loaded from Postgres alone, it would miss it. Step 3 closes that gap. The same message is sent again for every room if a server's Redis connection drops and comes back.

8.7 Idle rooms and restarts

When the last person leaves a room on a given server, that server starts a five-minute timer. If nobody returns, it saves anything unsaved, unsubscribes from the room's Redis channels and frees the memory. The next visitor, on any server, triggers a fresh load. This is what "stateless servers" means in practice: memory is only a cache of what Postgres holds.

A restart is the same story for all rooms at once: GracefulShutdown saves everything, the process exits, browsers reconnect elsewhere.
