Part 7The databases

There are two data systems. Postgres is where documents live permanently. Redis stores nothing; it only carries messages between servers.

7.1 Postgres in five minutes

  • A database contains tables. A table is like a spreadsheet: it has named columns, each with a type, and any number of rows.
  • A primary key is the column that uniquely identifies a row.
  • A foreign key is a column that points at a row in another table. Postgres refuses to let it point at nothing.
  • An index is a lookup structure, like the index of a book, that makes finding rows by a column fast.
  • A transaction is a group of changes that either all happen or none happen, even if the power fails in the middle.
  • bytea is the column type for raw bytes. Yjs updates are raw bytes, so this is what we store them in.

7.2 The three tables

rooms: one row per room

ColumnMeaning
idA random UUID generated by Postgres. Used internally to link the other tables.
slugThe 10-character id you see in the URL (/r/k3x9m2p7qa). Marked unique, so two rooms can never share one.
edit_token_hashA one-way fingerprint of the edit token. The token itself is never stored.
language, titleA copy of the room's settings, so the page can show them before the editor has connected.
created_at, last_active_atWhen the room was made, and when someone last edited it.

document_updates: the diary

An append-only log. Rows are only ever added (and later pruned by compaction); never modified. Each row is one Yjs update: a few bytes describing a few keystrokes. id is a bigserial, a number Postgres increases by one for every new row, which gives us the order in which rows were written. The index on (room_id, id) makes "all updates for this room, in order" a fast query.

document_snapshots: the summary

One row holds the entire document as a single Yjs update, as it stood when the snapshot was taken.

Both child tables declare ON DELETE CASCADE: deleting a room row automatically deletes its updates and snapshots.

Why it is built this wayThe obvious design is one column holding the current text, overwritten on every keystroke. That has two problems. It rewrites the whole document for each character typed. And it stores only the text, losing the CRDT bookkeeping (ids, origins) that makes merging possible. A log of updates is cheap to write (append a few bytes) and keeps everything. Its only weakness, a long replay when loading, is what snapshots fix.

7.3 The write path: how an edit gets saved

  1. A browser's update arrives and is applied to the room's in-memory document.
  2. Because it came from a browser on this server, the Room pushes it onto its dirtyUpdates list and starts a 500 ms timer if one is not already running.
  3. When the timer fires, Room.flush() takes everything on the list and writes it with a single statement: 
    INSERT INTO document_updates (room_id, update)
VALUES ($1, $2), ($1, $3), ($1, $4), …;
  4. It then updates rooms.last_active_at (and language / title if they changed).
  5. If the write fails, the batch is put back at the front of the list, in order, and retried. Typing continues meanwhile.

This is called debouncing: instead of one database write per keystroke, there is at most one every half second per room, however fast people type. On shutdown, every room is flushed immediately.

7.4 The read path: loading a room

When the first person connects to a room that is not in a server's memory, RoomHydrator rebuilds it:

1. SELECT * FROM document_snapshots
   WHERE room_id = $1 ORDER BY created_at DESC LIMIT 1;      → apply it, if any

2. SELECT id, update FROM document_updates
   WHERE room_id = $1 AND id > $cursor
   ORDER BY id LIMIT 500;                                   → apply each, repeat until none left

Step 2 reads in pages of 500 using the last id seen as a cursor (this is called keyset pagination), so even a room with tens of thousands of rows never loads them all into memory at once. Because updates are idempotent, it does not matter if a row overlaps with what the snapshot already contains.

7.5 Compaction: folding the diary into a summary

A busy room might gather thousands of update rows. Loading would get slower and slower. CompactionJob fixes this: every 60 seconds, for each room in memory with more than 1,000 rows, it runs the following inside one transaction:

  1. Take a lock for this room. pg_try_advisory_xact_lock(...) is a Postgres feature that lets programs agree "only one of us does this at a time". If another server already holds it, this one skips the room.
  2. Choose the cut. Read max(id) of the room's update rows. Call it N.
  3. Rebuild the document from the database only: previous snapshot plus update rows with id ≤ N.
  4. Insert a new snapshot containing that whole document.
  5. Delete the update rows with id ≤ N, and the older snapshot.
  6. Commit.
Why it is built this wayThe simpler idea, "save the document the server has in memory", is subtly wrong. Another server may have written rows this server has not received yet; deleting them would lose data. Building the snapshot from the database itself, up to a fixed row id, cannot lose anything. A test runs ten compactions at the same time as ten writers and checks the result character by character.

7.6 Migrations

A migration is a file of SQL that changes the database's structure: creating a table, adding a column. Migrations are numbered and applied in order, and Postgres remembers which ones have been applied, so running them again is harmless. Ours is packages/db/migrations/0000_cute_killraven.sql, which creates the three tables.

CommandWhat it does
pnpm db:migrateApplies every migration not yet applied. Run it once after creating the database, and again whenever a new migration appears.
pnpm db:generateAfter you edit a file in packages/db/schema/, this compares it with the last migration and writes a new SQL file for the difference.

7.7 Looking inside Postgres yourself

Try it 
psql synccode                                  # open the database
\dt                                            # list the tables
\d document_updates                            # describe one table

SELECT slug, language, title, last_active_at FROM rooms ORDER BY created_at DESC LIMIT 5;

-- how many update rows, and how many bytes, per room
SELECT r.slug, count(u.id) AS updates, sum(length(u.update)) AS bytes
FROM rooms r LEFT JOIN document_updates u ON u.room_id = r.id
GROUP BY r.slug ORDER BY updates DESC;

SELECT room_id, length(state) AS bytes, created_at FROM document_snapshots;
\q                                             # quit
Type a few lines in a room, wait a second, and run the second query again: the count goes up.

7.8 Redis: what is actually in it

Nothing is stored. Redis only relays messages on two channels per room. Each message is an envelope:

┌──────────────────┬────────┬───────────────────────────┐
│ node id          │ kind   │ payload                   │
│ 16 bytes         │ 1 byte │ N bytes                   │
└──────────────────┴────────┴───────────────────────────┘
   who published it   0 = update   1 = awareness   2 = sync-request
KindPayloadWhat a receiving server does
updateA Yjs updateApplies it and sends it to its own sockets
awarenessAn awareness updateApplies it and sends it to its own sockets
sync-requestThe sender's state vectorReplies by publishing whatever the sender is missing
Try itIn a terminal, run redis-cli psubscribe 'room:*'. Then type in a room in the browser. A line appears for every keystroke and cursor move (the contents look like gibberish because they are binary). Press Ctrl-C to stop.

If Redis is unavailable, servers stop hearing about each other's edits, but nothing is lost: each server still saves its own users' edits to Postgres, and they re-synchronise when Redis returns.
